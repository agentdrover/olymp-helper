# SPEC-1.0 — Олимпиадный помощник v1

Нормативный контракт продукта (ред. 5). Собран из трёх частей: §1–1.2, §1.3–1.3а, §1.4–1.8.
При расхождении с карточками хаба — вопрос в хаб, а не догадка.

## 1. Продукт

Пользователи: один ребёнок (7 класс) и один родитель (владелец).
Цель: подготовка к Всероссийской Сеченовской олимпиаде школьников по биологии, отборочный этап,
возрастная группа 5–7 классов. Химия отложена (у этой олимпиады химия с 8 класса).
Материалы: PDF с текстовым слоем (сборники заданий), учебники и конспекты в PDF.
Ключи ответов на сайте не опубликованы; ключ, если есть, загружается отдельным PDF.

### Решения владельца (22.10)
| Вопрос | Ответ |
|---|---|
| Олимпиада | Сеченовская, отборочный этап, биология 5–7 |
| Устройство | ноутбук/компьютер дома; доступ только из домашней сети |
| Модель | два канала: Claude CLI (подписка) и Cursor (cursor-agent CLI, ключ Cursor), переключение |
| Переписка | родитель видит итоги всегда, переписку — по запросу; ребёнок об этом знает |
| Материалы | PDF с текстом (без сканов и распознавания картинок) |
| Ввод | текст и голосовой ввод; режим «помоги задать вопрос»; без фото решений и без озвучки |
| Профили | один ребёнок + родитель |

### 1.1 Типы заданий v1
| Тип | Ввод ребёнка | Проверка |
|---|---|---|
| single | один вариант | равенство с ключом |
| multiple | набор вариантов | точное равенство множеств |
| match | пары «левый → правый» | равенство отображений целиком |
| open | — | **вне v1**: импортируется со статусом `unsupported`, ребёнку не показывается |

Задания, условие которых зависит от рисунка, схемы или таблицы, потерянной при извлечении текста, тоже получают `unsupported`.

**Рисунок задания (v1).** Задание с рисунком возвращается в банк так:
- Импорт пытается найти рисунок сам: места встроенных изображений на странице (PyMuPDF, координаты конкретного экземпляра) предлагаются рамкой рядом с заданием. Если поиск не удался — векторная схема без растрового объекта, страница-скан, несколько изображений — родитель рисует рамку сам; ручная рамка доступна всегда. Полностью отсканированный сборник без текстового слоя — вне v1.
- Координаты рамки хранятся в пунктах PDF в системе неповёрнутой страницы с учётом CropBox; рамка из пикселей рендера переводится делением на масштаб рендера, затем матрицей снятия поворота страницы и смещением начала CropBox (матрицы PyMuPDF), а не одним масштабом. PNG (двойное разрешение) рендерится из области страницы, а не извлекается как исходный объект, поэтому цифры и подписи на рисунке сохраняются.
- У рисунка два текста. `alt` — короткое описание для ребёнка и экранного диктора («продольный разрез цветка, цифрами 1–6 обозначены части»); его предлагает сервис, родитель правит. `teacher_note` — скрытое пояснение для модели: что обозначено каждой цифрой, что изображено; ребёнку не показывается никогда, используется только в запросах подсказок и объяснений — так же, как ключ.
- Модель картинку не видит и не получает. Задание с рисунком публикуется ребёнку только с подтверждённым ключом; `model_answer` для него не вычисляется. Подсказки и объяснения включаются, только если `teacher_note` достаточна: в ней упомянуто каждое обозначение, которое есть в вариантах ответа (каждая цифра или буква на рисунке), и родитель отметил «в пояснении названо, что обозначено». Иначе — режим «только проверка по ключу»: панель пишет «к этому заданию подсказок нет — проверь ответ по ключу»; разрешены две проверки, затем доступна только кнопка «Показать ответ» с подтверждением (итог «ответ показан после N попыток»); после верного ответа или показа — ответ ключа без объяснения. Это единственное исключение из правил 1, 2, 2а, 2в и 3 §1.3 (уточнение по ревью #2011): показ ответа по кнопке «Показать ответ» после двух проверок без подсказок допускается в этом режиме вместо верного ответа и подсказки 3; подсказок в режиме нет, поэтому правило 2а («проверок разрешено 2 + число взятых подсказок») даёт ровно две проверки. После показа состояние задания — `answer_shown` (новое состояние только для этого режима; дальнейшие проверки закрыты), в итоге занятия оно называется «ответ показан после N попыток, не разобрано» и не считается ни «верно», ни «решением по подсказке 3»; верный ответ, данный до показа, итог «верно с N-й попытки» не меняет.
- Перед подтверждением родитель отмечает «в рисунке и в описании нет ответа» (подписи, легенды, соседний текст). Сервер отклоняет `alt`, содержащий текст любого варианта ответа (нормализованное сравнение) или обозначение верного варианта.
- Если подписи на рисунке мельче читаемого размера при показе, задание остаётся `unsupported`.
- Ребёнок видит фрагмент над вариантами ответа с подписью источника («сборник 2022/23, стр. 3») и открывает его крупно (не меньше 560 px по ширине на ноутбуке). Проверка ответа — по ключу, как у обычного задания.
- Правка условия, рамки, `alt`, `teacher_note`, ключа или его источника создаёт новую ревизию задания и снимает отметку «проверено» до повторной проверки родителем; попытки и итоги ссылаются на ревизию (и версию ключа), по которой решал ребёнок; исправленный ключ применяется к новым попыткам, а в итогах старых попыток видна пометка «ключ исправлен после попытки». Для заданий без рисунка `model_answer` вычисляется после подтверждения условия родителем и пересчитывается при каждой новой ревизии.
Родитель может исключить такое задание или вручную ввести самодостаточное условие (тогда — обычная проверка).

### 1.2 Ключ и достоверность
- `answer_key` задания имеет источник: `official` (загруженный ключ, привязан к конкретному сборнику, варианту и номеру, подтверждён родителем) или `parent` (родитель вписал/подтвердил ответ сам).
- Проверка импорта (условие распознано верно) и подтверждение ответа — разные действия родителя.
- Без подтверждённого ключа: `correctness = unknown`; ответ модели хранится отдельно как `model_answer` с пометкой «не проверен». Пометка «ответ модели, не проверен» видна ребёнку и родителю во всех местах, где показан результат (экран задания, итоги, прогресс).
- Модель возвращает структурированный результат: `proposed_answer`, `explanation`, `uncertainty` (low|high). Расхождение с ключом — сравнение нормализованных ответов, не разбор текста.
- При расхождении: ребёнку показывается ответ ключа с пометкой «ответ уточняется у родителя», объяснение к нему не сочиняется; родителю — запись расхождения с ответом и объяснением модели. Ответ ключа ребёнку показывается ТОЛЬКО после того, как по правилам §1.3 допустимо открыть решение; до этого расхождение видно только родителю (уточнение по ревью #2011). `model_answer` вычисляется до публикации, поэтому расхождение может существовать уже до первой попытки ребёнка.
- **Без подтверждённого ключа решение открывается так же, как с ключом, но эталоном служит `model_answer`**: совпадение с ним переводит разбор в состояние `solved_unknown` (решение и объяснение показываются с пометкой «ответ модели, не проверен»); несовпадение — обычный разбор ошибки без раскрытия ответа модели; третья подсказка открывает решение модели с той же пометкой. `model_answer` вычисляет T05 после подтверждения условия родителем (и заново при каждой новой ревизии задания, см. 1.1) и фиксирует его до публикации; ребёнку до открытия решения он не виден. Если вычислить не удалось, родитель видит «ответ модели не получен — повторить», а задание без ключа и без `model_answer` ребёнку не публикуется.
- Защищаемое до открытия решения — не только ключ или `model_answer`: ни один ответ сервера не называет никакой вариант верным и не содержит полного решения; фильтр по обозначениям вариантов — дополнительная мера, не доказательство.
- Подтверждение ответа родителем сохраняет источник ключа: `official` — только для ключа, загруженного и привязанного к сборнику, варианту и номеру; ответ, вписанный родителем, остаётся `parent`.

### 1.3 Педагогические правила (нормативные)
Состояние разбора хранится на сервере: `new → attempted_wrong* → hint1 → hint2 → hint3 | solved | solved_unknown | answer_shown` (уточнение по ревью #2011) (`answer_shown` — только в режиме «только проверка по ключу», 1.1). Повторный разбор решённого задания — новая попытка с пометкой «повтор»; прежние события не стираются (кнопки «начать заново» нет).
1. Решение (верный вариант с объяснением) открывается только (а) после верного ответа, проверенного по подтверждённому ключу (без ключа — по 1.2), или (б) после запроса третьей подсказки с явным подтверждением ребёнка («Открыть решение? Задание засчитается как разобранное по подсказке»). Неверная попытка решение не открывает. Исключение — режим «только проверка по ключу» (1.1) (уточнение по ревью #2011).
2. Лестница подсказок: 1 — наводящий вопрос, 2 — ключевая идея, 3 — полное решение. Ступени идут по порядку; перескочить параметром запроса нельзя. Подсказка 1 доступна после первой попытки или через 60 секунд на экране задания (мягкий барьер против «прощёлкивания»). В режиме «только проверка по ключу» (1.1) подсказок нет и правило 2 не применяется (уточнение по ревью #2011).
2а. Неверные варианты не блокируются и не вычёркиваются: пометка «не то» стоит только у последнего проверенного выбора. Перебор не запрещается, но стоит подсказок: после второй неверной попытки каждая следующая проверка доступна только после очередной подсказки (проверок разрешено 2 + число взятых подсказок), и итог честно называет число подсказок. В режиме «только проверка по ключу» (1.1) подсказок нет, проверок ровно две, затем доступна только кнопка «Показать ответ» (уточнение по ревью #2011).
2б. Вместе с ответом ребёнок отмечает «уверен» или «сомневаюсь» (необязательно). Разбор ошибки при «уверен» отдельно разбирает, что именно сбило; в «Стоит вернуться» задания с «уверен и ошибся» идут первыми, затем остальные ошибки по давности.
2в. Итог попытки называется точно: с ключом — «верно с 1-й попытки», «верно с N-й попытки», «верно после подсказки N», «решение по подсказке 3»; без ключа — «совпало с ответом модели, не проверено» и «решение модели по подсказке 3, не проверено». Слово «верно» без ключа не используется. В режиме «только проверка по ключу» после показа ответа итог — «ответ показан после N попыток» (уточнение по ревью #2011).
3. До открытия решения ни один ответ сервера (страница, HTMX-фрагмент, ответ чата, JSON) не обозначает верный вариант и не раскрывает решение. Правило действует для чата и режима «помоги задать вопрос» тоже. Для изображений: до открытия решения ребёнку показывается только рисунок самого задания, подтверждённый родителем; `alt` рисунка проходит ту же серверную проверку, что и текст. Картинки страниц учебника и сами PDF ребёнку в v1 не отдаются вовсе: ссылка на учебник — текстовая цитата с номером страницы. Рендеры страниц и PDF доступны только родителю. Исключение: в режиме «только проверка по ключу» (1.1) ответ ключа (без объяснения) показывается после верного ответа или после «Показать ответ» с подтверждением (уточнение по ревью #2011).
4. Неверный ответ разбирается: почему вариант привлекателен и где ошибка, без раскрытия верного.
5. «Объясни иначе» (после открытия решения): проще; таблицей; на примере из жизни; «где ловят на олимпиаде»; «проверь, что я понял» (вопрос на перенос).
6. «Помоги задать вопрос»: помощник не отвечает по существу, а помогает сформулировать вопрос (уточняет, что непонятно, предлагает шаблон «чем отличается … от …?»).
7. Ключ главнее модели — см. 1.2.
8. Тон спокойный, без похвалы на каждое действие и без безусловной похвалы в итогах (итог — факты и один вывод «к чему вернуться»); «не уверен» — допустимо. Готовые формулировки в режиме «помоги задать вопрос» вставляются в поле для правки, а не отправляются за ребёнка.
9. Границы: только биология школьного уровня; посторонние темы — вежливый отказ и возврат к заданию. Никаких инструкций по опасным опытам, употреблению веществ, персональному лечению и диагнозам — вместо этого безопасное учебное объяснение и совет обратиться к взрослому.

### 1.3а Интерфейс: обязательные состояния и совместная работа
- Чат, голос и режим «помоги задать вопрос» живут в панели помощника на экране задания; отдельного пункта «Спросить» в навигации нет.
- Состояние запроса к модели в панели — один общий компонент; его делает T06, T07 использует его для чата и голоса без своего варианта.
- Состояния панели помощника: «думаю… обычно 5–15 с» (кнопки заблокированы, повторный запрос не уходит); «основной канал не ответил, пробую второй»; «помощник сейчас не отвечает — проверка по ключу работает»; «на сегодня вопросы кончились — проверка по ключу работает» (лимит). Голос: нет доступа к микрофону; страница открыта не по HTTPS; «распознаю…»; запись длиннее 30 с; распознанный текст можно поправить перед отправкой.
- «Показать родителю» (ребёнок): ребёнок сам открывает родителю переписку занятия или помечает задание «спорный ключ» — оно попадает в очередь проверки родителя с пометкой «от ребёнка».
- Счётчик дней до этапа — того же размера, что остальные цифры; родитель включает или выключает его в настройках (по умолчанию выключен).
- «Мои итоги» ребёнка — список занятий, журнал (только записи об открытии переписки родителем и о показе переписки ребёнком) и ссылка «Как это работает».
- Проверка заданий родителем — лента: исходная страница слева, карточка справа, счётчик «N из M», автопереход к следующему, клавиши: Enter — «верно и подтвердить», → — пропустить, E — поправить. Если ключ есть и модель согласна — одна кнопка «Верно, ответ X — подтвердить и дальше». Отдельные карточки: «ключа нет» (поле ответа → key_source=parent), «расхождение» (ключ, ответ и объяснение модели; «ключ прав» / «мой ответ …»), «нужен рисунок» (подтвердить найденный рисунок или поправить рамку, `alt`; либо ввести самодостаточное условие), «открытый — исключить», «спорный ключ от ребёнка».
- Открытие переписки родителем — с подтверждением «Запись появится в журнале ребёнка». Исключение: ребёнок сам показал занятие («Показать родителю») — подтверждение не нужно. В обоих случаях фактический просмотр пишет `parent_opened_chat`; показ ребёнком — отдельное событие `shown_to_parent`. Удаление переписки — по занятию и целиком, с подтверждением и счётом сообщений.
- Вход родителя: «неверный PIN, осталось N попыток», «вход закрыт до ЧЧ:ММ»; ввод цифр с клавиатуры; вход сразу после 4-й цифры.

### 1.4 Модель: каналы и изоляция
- Интерфейс `ModelChannel.complete(system: str, messages: list[{role: user|assistant, content}], schema) -> ModelResult{text|json, channel, model, duration_ms, usage|null, error|null}`. История передаётся явно; системные правила — только в `system`.
- Адаптеры: Claude — `claude -p --output-format json --model <m> --tools ""` плюс отключение MCP, пользовательских настроек и плагинов; Cursor — `cursor-agent -p --output-format json --model <m>` в режиме без записи и shell, если такой режим подтверждён для закреплённой версии.
- **Изоляция по построению**: CLI запускаются не в контейнере приложения, а в отдельном контейнере-исполнителе без тома с данными, с файловой системой только для чтения, пустым рабочим каталогом, минимальным окружением (только токен своего канала) и исходящими соединениями только к API своего провайдера. Приложение передаёт ему запрос по локальному сокету/HTTP. Даже если модель вызовет инструмент, ей нечего прочитать и некуда записать.
- Версии CLI закреплены в образе исполнителя; обезличенные образцы их JSON-ответов лежат в тестах.
- **Контейнер на канал, привилегии, рабочая область (уточнение по ревью #2013).**
  - Контейнеров-исполнителей два: `executor-claude` держит только `CLAUDE_CODE_OAUTH_TOKEN`, `executor-cursor` — только `CURSOR_API_KEY`; каждый обслуживает только свой канал. Один контейнер с обоими токенами не допускается.
  - Сервер исполнителя и CLI работают под разными UID (сервер — `exec-srv`, CLI — `exec-cli`, запуск через `setpriv` без привилегий и с `no-new-privs`): CLI не читает `/proc/<pid>/environ` сервера и не может вернуться в его UID.
  - Формулировка «некуда записать» уточняется: у CLI есть рабочая область — `tmpfs` в `/work` с ограничением размера и флагами `noexec,nosuid,nodev`; рабочий и домашний каталоги каждого запроса создаются в ней заново и удаляются после ответа. Тома с данными нет, корень только для чтения, исходящие соединения только к API своего провайдера.
  - Один запуск за раз на контейнер (уточнение по ревью #2013): параллельный запрос получает ответ «занят», и приложение трактует его как временный отказ (запасной канал по обычным правилам). До и после каждого запуска убиваются все процессы пользователя CLI (от его имени) и проверяется, что их не осталось; от предыдущего запуска не остаётся ничего живого. Каталоги запуска принадлежат пользователю CLI (0700), убираются от его имени. Таймаут убивает группу процессов от имени пользователя CLI.
  - Всё, что работает под пользователем CLI (сам CLI, убийство процессов, зачистка, уборка), запускается одним путём с явным минимальным окружением (PATH, HOME, LANG и токен своего канала только у CLI); окружение сервера, включая общий ключ, не наследуется. Уборка охватывает весь корень запуска, а не только рабочий и домашний каталоги. Состояние «неисправен» проверяется повторно под замком запуска.
  - Состояние пользователя CLI не переживает запуск (уточнение по ревью #2013, круг 5). В контейнере нет /dev/shm (ipc: none), вне каталога запуска пользователь CLI не пишет нигде (проверка обходит все каталоги и файлы, кроме /proc, /sys и /dev/mqueue). Всё остальное, чем он владеет, сбрасывает один шаг под пользователем CLI после каждого запуска и перед ним: убиваются все его процессы, удаляются очереди POSIX в /dev/mqueue и объекты SysV IPC (msg, shm, sem), убирается весь корень запуска. Затем проверка «ничего не осталось»: процессов нет, /dev/mqueue пуст, объектов SysV нет, корень удалён. Если что-то осталось, исполнитель неисправен. Основная защита (уточнение по ревью #2013, круг 6): лимиты IPC-пространства имён контейнера нулевые (kernel.msgmni, kernel.sem, kernel.shmmni равны нулю, kernel.shm_rmid_forced=1, fs.mqueue.queues_max=0), поэтому создать объект IPC нельзя и никакое состояние IPC не может пережить запуск; сброс и проверка — страховка, а проверка читает /proc/sysvipc (msg, shm, sem) и считает любой объект, чей бы он ни был, а также любой элемент /dev/mqueue.
  - Запрос к исполнителю принимается только с общим ключом приложения (`EXECUTOR_SHARED_KEY`, заголовок `X-Executor-Key`); без верного ключа — 401 и CLI не запускается; в окружение CLI ключ не передаётся.
  - Если процесс не удалось убить или каталог не удалось убрать, исполнитель неисправен: `/healthz` отвечает 503, запуски отклоняются, процесс выходит и политика перезапуска поднимает контейнер с чистым tmpfs.
  - Ответ исполнителя (в том числе успешный, текст и вложенный JSON) очищается от токенов до выхода из контейнера.
  - Остаточный риск: запрет shell и web у `cursor-agent` в режиме `--mode ask` не подтверждён; риск принят как остаточный риск изоляцией по построению (нет данных, нет чужих токенов, сеть только к провайдеру) и проверяется вживую в OH-T09.
- Ошибки: ненулевой код выхода, пустой или битый JSON, таймаут (120 с) — это ошибка, а не ответ. Ребёнок видит понятное сообщение без технических подробностей.
- Модель задаётся отдельно для каждого канала. Основной канал выбирается в настройках; при ошибке — одна попытка на запасном.
- Учёт: каждая попытка (в том числе запасная) атомарно записывается до запуска; единица учёта — запуск CLI; сутки по Europe/Moscow; дневной лимит запусков (по умолчанию 200, параллельные запросы не обходят лимит). По исчерпании — «на сегодня всё». Фактический канал, модель, длительность и факт переключения сохраняются и видны родителю.
- Секреты: `CLAUDE_CODE_OAUTH_TOKEN` выпускает владелец (`claude setup-token`) вне сборки и CI; `CURSOR_API_KEY` — из кабинета Cursor. Доставляются только при запуске на K8 через home-infra. В образ, репозиторий, логи и отчёты не попадают. Замена истёкшего токена описана в документе выката.

### 1.5 Недоверенные данные и вывод
- Текст PDF, фрагменты поиска, сообщения и расшифровки голоса — данные, не инструкции. Они передаются модели в отдельном размеченном блоке и не меняют системные правила, роли и состояние занятия.
- Весь текст из PDF и от модели экранируется при выводе; разрешённая разметка (Markdown) очищается от HTML и скриптов.

### 1.6 Данные ребёнка
- При первом входе — понятное уведомление: текст вопросов уходит внешней модели (Anthropic или Cursor); голос распознаётся дома и наружу не уходит.
- Модели передаётся минимальный контекст: задание, фрагменты учебника, последние сообщения занятия; без имени ребёнка.
- Аудио удаляется сразу после распознавания. Переписка хранится 180 дней, итоги — бессрочно; родитель может удалить переписку и материалы. Журналы CLI в контейнере-исполнителе не сохраняются (временный каталог очищается после запуска). Удаление на стороне провайдеров — по их правилам, это сказано в уведомлении.
- Изображения страниц и фрагменты рисунков — личное использование материалов семьи: хранятся только на томе `/srv/olymp`, моделям не передаются и наружу не отдаются.

### 1.7 Устройство
- Контейнер приложения: Python 3.12, FastAPI, шаблоны Jinja + HTMX, SQLite (WAL) и каталог файлов на томе `/srv/olymp`.
- Контейнер-исполнитель модели — см. 1.4.
- Поиск по учебникам: SQLite FTS5 по страницам; русский текст нормализуется одинаково для индекса и запроса — нижний регистр, ё→е, стемминг Snowball (пакет `snowballstemmer`, русский); запрос строится из токенов, без передачи пользовательского синтаксиса MATCH.
- Ссылки на источник: модель может ссылаться только на фрагменты, реально выданные поиском, по их серверным id; неизвестные id отбрасываются.
- Доступ: K8 в домашней сети (`192.168.0.138`). Голос требует secure context, поэтому HTTPS в LAN: свой корневой сертификат, сертификат сервера с SAN на `192.168.0.138` (и локальное имя, если будет), доверие на ноутбуке ребёнка. HTTP на адресе LAN исключением не является.
- Голос: MediaRecorder в браузере (поддерживаемый MIME определяется в браузере) → сервер → ffmpeg в mono PCM S16LE 16 кГц → whisper.cpp (закреплённая версия, multilingual `small`, веса с проверенной контрольной суммой в образе; во время работы ничего не скачивается). Запись до 30 с, очередь распознавания на 1 задачу, лимит CPU/памяти, `/healthz` отвечает во время распознавания. Память модели small ≈ 0,9 ГБ — учесть в резерве K8.
- Лимиты загрузки: PDF до 50 МБ и 400 страниц; обработка порциями по страницам с сохранением номеров; импорт идёт фоном со статусом и понятной ошибкой, не блокирует HTTP; повторная загрузка того же файла (по хэшу) дубликатов не создаёт.
- Рендер страниц сборника (для ленты проверки) — локально (PyMuPDF), лениво, с кэшем по хэшу материала и номеру страницы; лимит кэша 500 МБ, старые страницы вытесняются.
- Сеть K8: страж исходящего трафика `k8_guard` и георутинг; разрешение хостов провайдеров, установка контейнеров, секреты и HTTPS на K8 — задача в проекте home-infra (её заводит сессия K8, не этот проект).

### 1.8 Данные (минимум)
- `material`: id, файл, хэш, тип (tasks|key|textbook), олимпиада/год/этап/вариант, статус импорта, страницы (FTS5).
- `task_item`: id, material_id, страницы, вариант, исходный номер, subject=biology, type, text, options, points, topic, import_status (draft|checked|unsupported), answer_key, key_source (official|parent|null), model_answer, revision, figure (null | {file, material_id, page, rect — пункты PDF неповёрнутой страницы, alt, teacher_note, confirmed_by_parent}).
- `study_session`: id, начало, конец (явный «закончить» или 30 минут простоя), итог. При закрытии по простою конец = время последнего события (фактический конец активности); «закончить» после 30 минут простоя тоже закрывает занятие как простой (уточнение по ревью #2012).
- `event`: session_id, тип (attempt — с отметкой уверенности и признаком «повтор»|hint|answer_shown|explain|chat|voice|fallback|disputed_key|shown_to_parent|parent_opened_chat), task_item, данные, время — источник для итогов. Событие `answer_shown` (показ ответа кнопкой «Показать ответ» в режиме «только проверка по ключу», 1.1) пишется с числом попыток до показа (уточнение по ревью #2011), чтобы итог занятия «ответ показан после N попыток, не разобрано» строился из событий.
- `settings` дополнительно: показывать ли счётчик дней и дату этапа (поле `stage_date`, ISO-дата).
- `settings`: основной канал, модель на канал, лимит, хэш PIN родителя.
